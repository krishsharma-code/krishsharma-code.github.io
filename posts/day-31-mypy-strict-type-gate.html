Day 31: I Put a Strict Type Gate on My Python Portfolio — It Found 6 Real Bugs

24 November 2026 · Krish Sharma

Every gate in my Datheon Python Internship repo asks a question about execution. The test suite asks "does it run?". The coverage gate asks "is this line executed?". The mutation gate asks "do the tests have teeth?". The fuzzer asks "can I crash it?".

None of them asks the cheapest question of all: can a call be wrong without a test ever running?

That is the question a type checker answers on every commit, so on Day 31 I added one — mypy --strict, wired into CI, over every file that ships.

The problem: my annotations were a promise nobody checked

I am Krish Sharma (krishsharma-code), and this repo — Datheon_Python_Internship — is five Python projects sharing one core: a hangman game, a portfolio tracker, a file-organizer automation tool, a regex-driven terminal assistant, and an OOP inventory system. Every public callable has type hints. Every module has Google-style docstrings.

But "has annotations" and "annotations are correct" are different claims. My hints were documentation that nothing verified. A function could be annotated -> str and return None on one branch, and 1,800 passing tests would never notice if that branch was not exercised.

What the gate does

tools/typecheck.py runs mypy in six phases over 33 targets — every file that ships, nothing excused:

  • core — the thirteen shared modules plus the datheon package
  • 01_hangman_game … 05_inventory_oop — one phase per task pack
python tools/typecheck.py                # the whole gate
python tools/typecheck.py --json         # machine-readable verdict
python tools/typecheck.py --core-only    # skip the five project phases
python tools/typecheck.py --keep-shadow  # keep the shadow trees for triage

Exit codes follow the rest of the repo: 0 every phase clean and the config honest, 1 at least one error or finding, 2 the gate could not measure. A gate that cannot measure never reports success.

The shadow tree trick

projects/01_hangman_game starts with a digit, so it is not a valid Python package name — mypy refuses to look inside it at all. The tempting fix is to exclude the five projects, which would leave the largest part of the codebase untyped.

The gate does the opposite. For each project it builds a shadow tree — the shared core modules copied flat next to that project's files — which reproduces the module graph the CLIs actually create at runtime:

def build_shadow_tree(project: Path, destination: Path, root: Path = ROOT) -> Path:
    """Lay out one project's module graph flat in destination."""
    destination.mkdir(parents=True, exist_ok=True)
    for suffix in SHADOW_CORE_SUFFIXES:
        for core in sorted(root.glob(f"*{suffix}")):
            if core.is_file():
                shutil.copyfile(core, destination / core.name)
    for module in python_files(project):
        shutil.copyfile(module, destination / module.name)
    return destination

Copying is what lets mypy see the same import edges the interpreter sees, and it is also why the shadow tree needs --explicit-package-bases — without it mypy names files after the shadow directory and reports every one as "found twice under different module names".

The config is audited, not trusted

A gate is only as good as its scope, so the script compares [tool.mypy] files in pyproject.toml against [tool.setuptools] py-modules — what actually ships. Seven codes cover it: missing files, missing strict, a python_version that disagrees with requires-python, a shipped module with no files entry, a deleted py.typed, no CI step, and mypy missing from requirements.txt.

The scope check is the one that keeps it honest over time: add a fourteenth core module and the gate fails until it appears in both tables.

What it found on the first run

39 errors in 15 files. Six of them were not annotation gaps — they were defects:

The rest were honest gaps: a bare dict, a bare frozenset, a set with no element type.

None of these would have been caught by another test. That is the whole argument for the gate.

Wired into CI

One new job in .github/workflows/ci.yml:

type-check:
  name: Type check (mypy --strict)
  runs-on: ubuntu-latest

One runner, one interpreter. A type error is not a platform signal, so twelve copies of the job would cost minutes and prove nothing extra. The job is listed in the CI status aggregate — the single status a branch-protection rule can require.

Alongside it: docs/type_checking.md, 76 test functions for the gate itself, and datheon/py.typed so consumers' checkers actually read the annotations this gate just proved.

What it deliberately does not cover

  • tests/ — 48 files of fixture-heavy functions; pytest's fixtures are dynamic by design, and strict mypy there produces annotations that document nothing.
  • tools/ — the gates themselves; each has its own test module.
  • Runtime behaviour — a clean run says the calls agree with the signatures, not that the code is correct.

Each gate answers one question: pytest for "does it run", mutation.py for "do the tests have teeth", coverage_gate.py for "is it executed", typecheck.py for "do the calls agree with the signatures", benchmark_budget.py for "is it still fast".

Roadmap

  • Turn the six defects into regression tests so they cannot come back silently.
  • Run pyright alongside mypy — two independent checkers disagree in useful places.
  • Tighten the shadow-tree scope so the five projects are checked as packages instead of flat directories.

Conclusion

Day 31 was not a feature day. It was the day the repo started asking a question it had never asked before, and the answer on the first run was "yes, the calls were wrong in fifteen files".

If you are building anything in Python that other people install, add this gate. It costs one CI job and it pays for itself the first time it catches an Optional you forgot.

The repo is open: github.com/krishsharma-code/Datheon_Python_Internship — star it, read docs/type_checking.md, or open an issue if you spot something the gate missed.
