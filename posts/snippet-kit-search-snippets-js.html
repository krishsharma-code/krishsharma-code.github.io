Your Search Snippet Cuts a Word in Half — and Unicode Notices

28 November 2026 · Krish Sharma

Open any search page and read the second result closely. The bold starts in the middle of a word. An ellipsis appears where a sentence should have continued. A two-word query bolds one word twice and wraps it in two nested tags, and a result written in Hindi or Tamil comes back with the highlight shifted by three characters because somebody called toLowerCase() on a string and trusted the offsets afterwards.

None of this is hard to fix. All of it is easy to forget. That is the space snippet-kit lives in — a module I added to daily-dev-workspace this week: a pure ES module over strings, with no DOM, no dependencies and no build step.

The problem: a snippet is four problems wearing one hat

The naive version takes the text, calls indexOf, slices 80 characters either side, wraps the match in <mark> and renders it. It works on demo data and fails in production for four separate reasons.

The query is not a string. In "credit note" refund the quotes mean one phrase and the bare word means a second term. Split on whitespace and two of your three terms match places the user never asked about.

Matches overlap. Search for gst invoice and the phrase and the word gst match the same characters. Emit a range per term and the renderer produces <mark>gst <mark>invoice</mark></mark> — invalid nesting that browsers silently repair by moving your tags.

Offsets drift. toLowerCase is not length-preserving: the Turkish dotted capital İ lowercases to two code units. Fold the haystack, find a match at 40, slice the original at 40, and everything after that point is off by one.

The cut lands anywhere. A fixed width splits words, splits a surrogate pair so an emoji renders as two replacement characters, and separates a Devanagari base letter from its vowel sign.

And one security bug on top: a snippet is user content rendered as HTML. Unescaped, it is an injection.

How it works: offsets first, markup second

One rule runs through the module: every function returns offsets, never markup. findMatches() gives { start, end } pairs with an exclusive end, like String.prototype.slice. Rendering is a separate decision — annotate() turns offsets into plain and matched segments for a framework, highlightHtml() into an escaped string.

Matching is a scan, not a regex. Each term walks the haystack with indexOf, resuming from at + 1 so overlapping occurrences are seen; the ranges then pass through mergeRanges(), which sorts by start and collapses anything that overlaps or touches. One word, one <mark>, always.

Case folding is the care that makes offsets trustworthy. fold() walks the string character by character and keeps the original whenever its lowercase form would change length, so the haystack is the same length as the text and an index into one is an index into the other.

Windowing is where the module earns its keep. computeWindow() anchors on the first match, opens about 35% of the budget ahead of it, widens if a match straddles an edge, trims the roomier side back to budget, snaps to whitespace within 24 characters, then hands the result to two guards — unchanged from snippet-kit.js:

/** Never begin a window on a low surrogate or an orphaned combining mark. */
function safeStart(text, index) {
  let i = Math.max(0, Math.min(index, text.length));
  if (i > 0 && i < text.length && isLowSurrogate(text.charCodeAt(i))) i -= 1;
  if (i > 0 && i < text.length && COMBINING_MARK.test(charStartingAt(text, i))) i -= 1;
  return i;
}

/** Never end a window between a high surrogate and its pair, or before a mark. */
function safeEnd(text, index) {
  let i = Math.max(0, Math.min(index, text.length));
  if (i > 0 && i < text.length && isHighSurrogate(text.charCodeAt(i - 1))) i -= 1;
  if (i > 0 && i < text.length && COMBINING_MARK.test(charStartingAt(text, i))) i += 1;
  return i;
}

Word snapping is best-effort and knows it. If no space turns up within 24 characters — a long URL, a base64 blob — the guards still run and the window is cut at the character limit instead of dropped.

Output passes through escapeHtml() — & < > " ' — before any tag is added, so snippetHtml() escapes the text, wraps matched runs in <mark> (or your tag and class) and adds an ellipsis only where something was trimmed. snippet() returns those two facts as booleans, so a React or Svelte caller can render its own affordance instead of parsing a string.

What's new in this release

This week's commit (9fa83a0, feat(web-frontend): add snippet-kit for safe search-result snippets) adds the module under web-frontend/snippet-kit/:

  • Queries with phrases. parseQuery() turns "gst invoice" refund into one phrase term and one word term, drops case-insensitive duplicates and puts longer terms first. "credit note" returns one range; unquoted, it returns two.
  • Two shapes of input. terms is a query string or an array of strings and { text, phrase } objects, so a query parsed once can be reused across many documents.
  • Whole-word matching when you want it. wholeWord: true rejects matches glued to a letter, digit or underscore, so gst no longer matches inside gstr.
  • A useful no-match result. A query that misses returns the head of the text, matched: 0 and an empty range list — never an empty string.
  • 30 tests and a browser demo. node --test covers parsing, merging, escaping, Unicode offsets and the window edge cases; index.html searches six sample support tickets, one in Devanagari, and prints the ranges the first result returned.
  • Listed where it can be found. The module is in web-frontend/README.md with a one-line description, alongside the rest of the collection.

The demo output above is worth reading once. The phrase "credit note" matches the policy document at range 2–13, gst matches the first ticket at 28–31, and the Devanagari ticket reports no match rather than a broken one. The last two lines show why offsets matter: चालान comes back as 11–16 on Devanagari text, and annotate() splits a sentence into five segments, three plain and two matched.

Roadmap

Next steps; none of these exist in the repo yet:

  • Grapheme-aware windowing via Intl.Segmenter, so an Indic conjunct cluster is treated as one unit rather than as a base plus marks.
  • A ranking helper that scores documents by match count and position.
  • A configurable cap on ranges per document, so a document that mentions the term forty times does not produce forty highlights.
  • TypeScript declaration files, generated from the JSDoc that is already in the source.

Conclusion

A snippet is a promise about where a match lives, expressed in offsets and rendered as markup much later. Get the offsets right and rendering is a loop. Get them wrong and no amount of CSS saves the page: the highlight drifts, the words break, and the reader sees a sentence that was never written.

Merged ranges, length-preserving case folding, boundary snapping and escaped output are four small decisions that turn a 160-character cut into something a reader can trust.

The code is open: daily-dev-workspace/web-frontend/snippet-kit. Clone it, run node --test to see the thirty cases pass, then open index.html and search the sample tickets yourself — and tell me which snippet bug your own search box still ships, or open an issue if you find a window case this module cuts badly.
