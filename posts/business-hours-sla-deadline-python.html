Your 8-Hour SLA Deadline Is a Lie After 6 p.m. on Friday

27 November 2026 · Krish Sharma

A support ticket arrives at 17:00 on Friday. The promise attached to it says we reply within 8 working hours. Add eight hours with timedelta and the system prints a deadline of Saturday, 01:00 — a moment when nobody at the desk exists, on a day the desk is not open.

The customer is told a deadline that no team can meet. The engineer who picks the ticket up on Monday is already late. And the dashboard that reports SLA breaches will be reporting a fiction, because every one of those breaches was created by arithmetic, not by work.

That gap — between elapsed hours and working hours — is what the new business-hours module in my daily-dev-workspace repository closes. It is pure standard library: datetime and zoneinfo, nothing else.

The problem: closed time is not a small correction

Subtracting two timestamps gives you a number that is correct and useless. An 8-hour SLA opened on Friday evening is really 1.5 hours before the weekend, then 6.5 hours from Monday morning. Between those two facts sits a weekend, and if there is a public holiday on Monday, a third day disappears from the count too.

Teams usually patch this with a helper that adds days until the hour falls inside 09:00–17:00. That works until the first lunch break, the first split shift, the first holiday, or the first server that stores UTC while the desk works in IST. Then the helper quietly starts lying again, and nobody notices until a customer quotes a deadline back at you.

How it works: resolve the day, then walk the windows

The module has one idea. A BusinessCalendar knows three things: which weekdays are open, which hours of those days count, and which dates are holidays. Everything else is arithmetic on top of that.

segments(day) is the single source of truth. Given a date, it returns the open intervals as (start, end) datetime pairs — already resolved against the holiday set, already merged when two windows overlap or touch. Every other method reads from it, which is why a holiday, a split shift and an ordinary Tuesday all behave the same way.

Here is the real forward walk from business_hours.py, unchanged:

    def _add(self, cursor: datetime, remaining: timedelta) -> datetime:
        for day in self._days_forward(cursor.date()):
            for start, end in self.segments(day):
                point = max(cursor, start)
                if point >= end:
                    continue
                available = end - point
                if available >= remaining:
                    return point + remaining
                remaining -= available
                cursor = end
        raise NoOpenWindowError("no open window found within the search range")

Four lines carry the whole contract. point = max(cursor, start) is the clipping rule: arriving at 07:00 for a 09:30 opening does not charge you two and a half hours of waiting, it starts the clock at 09:30. if point >= end: continue is the exclusive-close rule: a window ending at 18:30 does not contain 18:30, so the walk moves to the next segment instead of charging zero. available is what is left of this window, and the last line spills the remainder into the following one.

_subtract is the mirror image and runs the segments of each day in reverse, stepping to the previous day from its last instant so every window on it is fully available. That is what makes "8 working hours before Monday 18:30" land at Monday 10:30 rather than somewhere inside the weekend.

Two smaller decisions are worth naming. Overnight windows are rejected at construction time — a window whose close is not after its open raises ValueError instead of guessing at a midnight rollover. And the walk is bounded by MAX_DAYS = 3660, roughly ten years, so a calendar whose windows can never match the input raises NoOpenWindowError (a ValueError subclass) instead of looping forever.

What's new in this release

This week's commit (f54cc44, feat(python): add business-hours calendar for SLA deadlines) adds the whole module under python/business-hours/:

  • Two ways to describe a week. BusinessCalendar(("09:30", "18:30"), workdays=..., holidays=..., tz=...) for one window per day, and BusinessCalendar.from_windows({0: [("09:00", "13:00"), ("14:00", "18:00")]}) for a lunch break or a shift that differs by weekday.
  • The queries you actually need. add_business_hours() for deadlines, business_time_between() for elapsed open time, plus is_open(), next_open(), is_workday() and segments().
  • Deadlines that walk backwards. add_business_hours() accepts an int, a float or a timedelta, and a negative value runs _subtract instead.
  • Real timezones. With tz="Asia/Kolkata", naive input is read as wall-clock time in that zone and results come back zone-aware; aware input is converted into it. With tz=None the calendar works on naive datetimes and rejects aware ones rather than comparing across zones by accident.
  • Tolerant input, strict output. Hours accept "09:30", "9:30", "09:30:00" or a time; holidays accept date, datetime or "YYYY-MM-DD"; an overlapping pair of windows is merged so double-booked shifts count once.
  • 45 tests and a runnable example. The suite covers the arithmetic, the parsing and the error paths; python example.py prints the SLA walk-through shown above.

The module is listed in python/README.md alongside the rest of the collection, so it is discoverable without knowing the path.

Roadmap

Directions I want to take next; none of these exist in the repo yet:

  • A per-day timezone override for desks that follow the customer's zone, not the team's.
  • Named holiday calendars loaded from a small JSON file, so a year of dates is not hard-coded at the call site.
  • Half-day holidays, which are currently all-or-nothing.
  • A batch helper that answers "which of these 500 tickets breach by Friday?" in one pass instead of 500 walks.

Conclusion

An SLA is a promise expressed in working hours, and software that stores it as a timestamp is storing a different promise than the one the customer was given. The fix is not a bigger scheduling product. It is deciding once what "open" means — which days, which hours, which holidays, which zone — and then counting nothing else.

Closed time gets skipped, never charged. That single rule is the whole module, and it turns a Friday evening ticket into a Monday deadline you can actually keep.

The code is open: daily-dev-workspace/python/business-hours. Clone it, run python example.py to see the walk-through, then point it at your own support desk — and tell me which holiday your current SLA calculator still gets wrong, or open an issue if you find a window case the walk misses.
